# Product

## Register

product

## Users

SD Proxy serves power creators who generate, compare, refine, and organize AI images across multiple local and hosted backends. They are often deep in a long creative session, switching between prompt writing, backend-specific controls, queue management, history review, gallery curation, and occasional API or deployment configuration.

These users value speed, precision, and control. They need the interface to keep complex options close without making the workspace feel chaotic, childish, or generic.

## Product Purpose

SD Proxy is a multi-backend image generation proxy and web workbench with login protection and an OpenAI-compatible API. It helps creators move fluidly across A1111, ComfyUI, NovelAI, PixAI, Naistera, Gemini, Kie.ai, CivitAI, Stability, Replicate, Fal.ai, Together AI, and custom providers.

Success means three things working together: faster generation workflows, safer backend and API management, and better creative organization. The product should make repeated expert actions efficient, make backend differences legible, and preserve useful creative history without turning the tool into a heavy admin system.

## Brand Personality

Creative, expert, precise.

The voice should be compact and capable. It should feel like a serious creator's workbench: direct labels, clear state, confident affordances, and enough personality to support creative flow without competing with the images or settings.

## Anti-references

SD Proxy should not feel like a generic SaaS dashboard, a toy image app, a crypto or neon tool, a corporate admin panel, or a maximalist visual playground.

Avoid decorative metrics, vague marketing copy, huge empty panels, loud novelty styling, and interface chrome that competes with prompts, generated images, settings, logs, and history.

## Design Principles

1. Keep expert controls close.
   Common generation, queue, backend, and prompt actions should be reachable without ceremony. Complexity should be organized, not hidden behind slow navigation.

2. Let backend differences explain themselves.
   Each provider has different capabilities, costs, limits, and model conventions. The UI should make those differences visible at the moment of choice.

3. Make creative history usable.
   Prompts, settings, results, favorites, folders, and tags should support recall, comparison, and remixing. History is part of the creative workflow, not a passive archive.

4. Protect remote and shared use.
   Login, API access, local URL safety, session isolation, queue state, and logs should read as trustworthy and understandable without turning the product into a corporate console.

5. Preserve focus during long sessions.
   The interface should be dense but calm, with clear hierarchy, compact copy, stable controls, and visual restraint so images and decisions remain the center of attention.

## Accessibility & Inclusion

Use WCAG AA as the baseline. Support keyboard-friendly workflows, visible focus states, reduced-motion preferences, readable text at dense UI sizes, and color-blind-safe status communication that never relies on color alone.
